# エージェント向け手引き: このリポジトリの `.review.yml` / `.review/` を作成する

> English version: [agent-review-setup.md](agent-review-setup.md)

このファイルは、[gitbucket-llm-reviewer](https://github.com/takahino/coderabitlikelocalllm)（GitBucketのプルリクエストをローカル/セルフホストLLMでレビューする、CodeRabbit風のツール）によるレビュー対象となるリポジトリで作業するAIコーディングエージェント（Claude Code等）向けの、**それ単体で完結する指示書**です。

## この手引きの使い方

人間がこのファイルをレビュー対象リポジトリにコピーする（またはこの内容をプロンプトに貼り付ける）などしてAIエージェントに渡し、「この手引きに従って、このリポジトリ用の `.review.yml`（必要なら `.review/` も）を作成して」のように指示することを想定しています。エージェントは、このリポジトリの実際のコードやドキュメントを調査したうえで、そこから見えてくる内容に即した `.review.yml`（および必要なら `.review/*.md`）を作成してください。汎用的なテンプレートをそのまま流用するのではなく、このリポジトリ固有の内容にすることが重要です。

この手引きは、レビューツール本体のリポジトリにある `review.example.yml` やソースコードが手元に無くても読めるように、必要な情報をすべてこのファイル内に自己完結させています。

## 重要: 設定ミスは「エラーなく静かにスキップ」される

レビューツールは、PRをレビューする前にこのリポジトリの**ルート**にある `.review.yml` を読み込みます。このファイルが存在しない、YAMLとして不正、または `perspectives`（観点）が実質0件に解決される場合、**このリポジトリのレビューはエラーも出さず静かにスキップされます**。デフォルト観点へのフォールバックはありません。つまり、トップレベルのキー名を1文字間違えるだけでも、気づかれないままレビューが永久に無効化される可能性があります。このため、後述のセルフチェックは省略可能な手順ではなく、作業の一部として必ず実施してください。

## `.review.yml` とは何か（何でないか）

- リポジトリの**ルート**に `.review.yml`（先頭ドット付き）として配置する必要があります。サブフォルダに置いても無視されます。モノレポでフォルダ毎に観点を分けたい場合は、後述の `paths:` を使ってください（`.review.yml` を複数配置する方式ではありません）。
- ここで定義するのは**レビュー観点(perspectives)**と、それに付随するいくつかの設定であり、接続情報・認証情報・LLMモデル設定ではありません。それらはレビューツール側の `config.yml` にあり、このリポジトリには含まれず、この手引きに基づくエージェントが触るべきものでもありません。
- トップレベル・ネストいずれのキーも、未知のキーは**エラーにならず黙って無視されます**。キー名のtypoはパースエラーにならず、単にその項目が何も効かなくなるだけです。下記のスキーマ表と照らしてキー名を正確に確認してください。

## `.review/` フォルダとは何か（何でないか）

- `.review.yml` と同階層（リポジトリルート）に置く任意のフォルダで、`perspectives` エントリの `context:` リストから名前で参照されるMarkdownファイルを格納します（スキーマ詳細は後述）。これらのファイルは、対応する観点が適用されるレビューの際に、検索を介さず毎回全文がLLMに渡されます。
- カテゴリ別にサブフォルダで整理してください（例: `domain-knowledge/`, `architecture/`, `dsl/`, `coding-rules/`, `must-follow/`）。フォルダ名・階層は自由です。
- それ以外の用途には使いません。特に、レビューツール自身のローカル状態ファイル（`review-state.json` やRAGベクトルインデックス等）とは**無関係**です。それらはレビューツールを動かしているマシン側にあり、このリポジトリの中には存在しません。この手引きに基づくエージェントが、それらをこのリポジトリ内に作成・参照することは決してしないでください。

## スキーマ一覧

特記のない限りすべて任意項目です。省略した場合は表のデフォルト値が使われます。

| キー | 型 | デフォルト | 説明 |
|---|---|---|---|
| `language` | 文字列 | `"ja"` | LLMがレビューコメントを書く言語。ツールのプロンプトは日本語向けに作られており、他の言語は完全にはサポートされていません。 |
| `perspectives` | リスト | `[]`（空だとレビュー自体スキップ） | リポジトリ全体に適用する観点。書式は後述「観点エントリの書式」を参照。 |
| `paths` | glob→設定のマップ | `{}` | モノレポ向け、フォルダ毎の追加観点/追加コーディング規約。キーはJava NIO `PathMatcher` の `glob:` 構文（正規表現ではない）で変更ファイルパスに対してマッチ判定される。例: `"frontend/**"` |
| `paths.<glob>.perspectives` | リスト | `[]` | このglobにマッチしたファイルに「追加」される観点（置き換えではない）。 |
| `paths.<glob>.inherit` | 真偽値 | `true` | `true` ならこのglobにマッチしたファイルにも共通の `perspectives`/`knowledgeBase` が適用される。`false` ならこのglob固有の設定のみが適用される。 |
| `paths.<glob>.knowledgeBase` | パスのリスト | `[]` | このglob配下にのみ追加されるRAG検索対象文書（下記 `knowledgeBase` 参照）。 |
| `exclude` | globのリスト | `[]` | diffから完全に除外するファイル。変更ファイル一覧に現れず、`paths` のマッチング対象にもならない。ビルド生成物・minifyファイル・ロックファイル等に使う。 |
| `contextFiles` | パスのリスト | `[]` | 観点に関係なく毎回無条件で全文をLLMに渡すファイル（リポジトリルートからの相対パス）。全レビューで本当に有用な小さいファイルにのみ絞って使う(例: `README.md`)。 |
| `knowledgeBase` | パスのリスト | `[]` | RAGベクトル検索の対象とするコーディング規約文書。**レビューツール側の `config.yml` で `rag.enabled: true` の場合のみ有効**で、それ以外では黙って使われない。`perspectives[].context` との違いは、全文ではなく類似度の高いチャンクのみが提示される点。 |
| `maxComments` | 整数 | `10` | 投稿コメントに"表示"する指摘事項の最大件数（LLMが検出する件数自体を制限するものではない）。 |

### 観点エントリの書式

`perspectives`（および `paths.<glob>.perspectives`）の各要素は次のいずれか:

1. スカラー文字列 — 観点のテキストのみ、追加コンテキストなし。「〜を確認して」のような指示文でも「〜の一貫性」のような名詞句でもよい。
2. `perspective`（テキスト）と `context`（`.review/` からの相対パスのリスト）を持つマッピング — その観点に `.review/` の参考ドキュメントを紐づけたい場合に使う。

```yaml
perspectives:
  - "セキュリティ(インジェクション、認可漏れ)"
  - perspective: "独自DSLのバリデーションルール整合性"
    context:
      - "dsl/spec.md"                      # .review/dsl/spec.md を読み込む
      - "must-follow/security-checklist.md"
```

### 完成例

```yaml
language: ja
perspectives:
  - "セキュリティ(インジェクション、認可漏れ)"
  - "既存コードとの命名・設計の一貫性"
  - perspective: "独自DSLのバリデーションルール整合性"
    context:
      - "dsl/spec.md"
paths:
  "frontend/**":
    perspectives:
      - "React hooksの依存配列漏れ"
      - "XSS(dangerouslySetInnerHTML等)"
    inherit: true
    knowledgeBase:
      - "frontend/docs/coding-standards.md"
  "backend/**":
    perspectives:
      - "トランザクション境界の妥当性"
      - "N+1クエリ"
    knowledgeBase:
      - "backend/docs/coding-standards.md"
exclude:
  - "**/*.min.js"
contextFiles:
  - "README.md"
knowledgeBase:
  - "docs/coding-standards.md"
maxComments: 10
```

```
.review.yml
.review/
├── domain-knowledge/
│   └── payment-flow.md
├── architecture/
│   └── overview.md
├── dsl/
│   └── spec.md
├── coding-rules/
│   └── naming.md
└── must-follow/
    └── security-checklist.md
```

## エージェントの作業手順

1. **リポジトリを調査する。** 主要な言語/フレームワーク、モノレポ構成かどうか(`frontend/`・`backend/`のような、独立した構造を持つトップレベルフォルダが複数あるか)、既存のコーディング規約文書(`CONTRIBUTING.md`, `docs/coding-standards.md`, ADR等)、既存のlint/security設定の有無を確認する。これらはそのコードベースで既に重視されていることのヒントになる。
2. **`language` を決める。** 人間から特に指示がない限り、リポジトリ自身のドキュメント・コメントで使われている言語に合わせる。
3. **共通 `perspectives` を起草する。** ここが最も重要なステップ。「バグがないか確認」「良いコードを書く」のような汎用的な項目は避け、各観点を*このリポジトリ固有*の具体的な事柄に根ざしたものにする。判断フレームの例:
   - **スタック固有のセキュリティ懸念** — 例: Spring MVCアプリでの `@PreAuthorize`/認可チェック漏れ、Reactでの `dangerouslySetInnerHTML` 誤用、生SQLの文字列結合。
   - **既存パターンとの一貫性** — そのコードベースで既に確立されている命名規約、レイヤリング、エラーハンドリングのスタイル。
   - **ドメイン/ビジネスルールの正しさ** — diffが気づかれずに破りうる、このリポジトリのドメイン固有の不変条件。
   - **そのスタックで既知のパフォーマンス落とし穴** — ORMを使うバックエンドならN+1クエリ、Reactフロントエンドなら不要な再レンダリング等。
   各観点は、レビュアーが「このdiffはこの観点を満たしている/満たしていない」と具体的に指摘できるものであるべきで、抽象的な心構えであってはならない。
4. **モノレポであれば `paths` を追加する。** 構造的に異なる領域ごとに1つのglobエントリを設け、その領域のスタックに即した観点を書く。`inherit` はエントリごとに判断し、通常は `true` のままでよいが、その領域が共通観点とは無関係なほど性質が異なる場合は `false` にする。
5. **`exclude` を追加する。** ビルド成果物・生成コード・minifyされたアセット・ロックファイルなど、diffに含めてもノイズにしかならないものを指定する。
6. **`contextFiles` は最小限に留めて追加する。** すべてのレビューで本当に有用な小さいファイルのみ(多くの場合 `README.md` のみ、あるいは不要)。
7. **`knowledgeBase` は、人間からRAGを有効化する(`config.yml` の `rag.enabled: true`)意向が示されており、かつインデックス化する価値のある既存のコーディング規約文書がある場合のみ**追加する。それ以外は省略する。
8. **必要に応じて `.review/` の中身を作成する。** diffだけではLLMが妥当に推測できないドメイン知識・独自DSL/仕様・厳守事項が必要な観点については、適切な名前の `.review/<カテゴリ>/` サブフォルダにMarkdownファイルを作成(または既存のリポジトリ内ドキュメントから転記)し、その観点の `context:` リストから参照する。内容を捏造しないこと — 実際にリポジトリ内に存在する情報(既存ドキュメント、コードコメント、仕様書等)に基づいて書くこと。裏付けとなる情報源が無い場合は、`context:` の追加自体を見送る。

## 完了前のセルフチェック(必須。前述の「静かにスキップされる」注意を参照)

- [ ] `.review.yml` が**リポジトリのルート**にあり、サブフォルダに置いていないか。
- [ ] 有効なYAMLであり、`perspectives` が1件以上に解決されるか。
- [ ] 使用したトップレベルキーがすべてスキーマ表通りに正確な綴りか(`language`, `perspectives`, `paths`, `exclude`, `contextFiles`, `knowledgeBase`, `maxComments`) — 未知のキーはエラーにならず黙って無視される点に注意。
- [ ] `context:` に列挙した全ファイルが、解決後のパスで実際に `.review/` 配下に存在するか。
- [ ] `paths` の各キーが、このリポジトリの実在するファイルに実際にマッチするglobになっているか(glob構文であり正規表現ではない)。
- [ ] `contextFiles`/`knowledgeBase` に列挙したパスが実際にリポジトリ内に存在するか。

## アンチパターン

- このリポジトリ固有の何かを参照しない、曖昧・一般論的な観点(例:「きれいなコードを書く」「バグがないか確認」)。
- 存在しないファイルを `context`/`contextFiles`/`knowledgeBase` に書くこと。
- `.review.yml` をリポジトリルート以外に置くこと。
- `perspectives` を空のままにすること — 目に見えるエラーもなく、そのリポジトリは永久にレビューされなくなる。
