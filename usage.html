gitbucket-llm-reviewer 詳細ガイド

GitBucket のプルリクエストをポーリングで監視し、OpenAI互換API経由のローカルLLMで 自動コードレビューを行うJava 21製アプリケーションの運用マニュアルです。 大量修正PRではdiffを切り捨てずファイル境界で複数バッチに分割してレビューします。 セットアップから設定ファイルの全項目、バッチ分割・Nパスによる全体整合チェックの内部動作まで、 実際に運用する上で必要な情報をまとめています。

→ すぐに動かす config.yml 全項目 .review.yml 全項目 バッチ分割・Nパスの仕組み メンション応答 RAG設定 うまく動かない時

01全体像

1プロセスの常駐アプリケーションが、監視対象リポジトリを定期的に走査します。 diffの取得はGitBucketのgit smart HTTPに対するJGitフェッチを主経路とし、 失敗した場合のみREST APIのコミット単位パッチ連結にフォールバックします。 LLM呼び出しはlangchain4j経由で行い、rag.enabled: true の場合は ベクトル検索によるコンテキスト拡張(RAG、詳細は「08」)が加わります。

図1: 実線の矢印がJGit経由の主経路、破線がAPIフォールバック経路。LLMとReviewOrchestratorの間の点線ループは need_more_context による追加ファイル要求の往復を表す(詳細は「07 レビューの流れ」を参照)。

02必要要件

項目要件
Java21 以上
Maven3.9 以上
GitBucket稼働中のインスタンス(4.46.1で動作確認済み)とAPIトークン
LLMエンドポイントOpenAI互換の /chat/completions を持つサーバー(Ollama / LM Studio / vLLM 等)
ネットワーク本ツールからGitBucketのHTTP(S)・git smart HTTP、およびLLMエンドポイントへの到達性

03セットアップ

初回起動までの実際の手順です。上から順に実行してください。

  1. ビルドする

    プロジェクトルートで実行可能なfat-jarを生成します。

    bash 
    # target/gitbucket-llm-reviewer.jar が生成される
mvn package

  2. ツール側設定ファイルを作成する

    config.example.yml を config.yml としてコピーし、実際の値を設定します。 config.yml は .gitignore 済みなので、実トークンをコミットしてしまう心配はありません。 RTX5090(VRAM 32GB)・RAM 128GB級のハイスペック環境で大型モデルを運用する場合は、各種上限を緩和済みの config.example_high.yml をベースにしてもかまいません。

    bash 
    # 一般的な環境向け
cp config.example.yml config.yml
# ハイスペック環境向け(VRAM/RAM潤沢・大型モデル運用時)
# cp config.example_high.yml config.yml

    最低限、以下の3項目は必ず自分の環境の値に書き換えてください(各項目の意味は「04 config.yml リファレンス」で解説)。

    config.yml(抜粋) 
    gitbucket:
  baseUrl: http://localhost:8080   # 自分のGitBucketのURL
  token: "xxxxxxxx"            # GitBucketで発行したAPIトークン
repositories:
  - owner: root               # 監視したいリポジトリのowner
    name: sample-repo         # 監視したいリポジトリ名

  3. リポジトリ側にレビュー観点を配置する(必須)

    review.example.yml を参考に、レビュー対象リポジトリのルートに .review.yml として配置します。.review.yml が無い、または解析に失敗した場合は観点が0件となり、 そのリポジトリのレビュー自体がスキップされます(観点を明示的に設定したリポジトリのみがレビュー対象になります)。

    bash 
    # レビュー対象リポジトリ側での作業
cp review.example.yml .review.yml
git add .review.yml && git commit -m "add review perspectives"

    観点ごとにドメイン知識・独自DSL・独自コーディングルールなどの追加コンテキストを渡したい場合は、 .review.yml と同階層に .review/ フォルダを置きます(詳細は「05 .review.yml リファレンス」)。

  4. まずは --once --dry-run で試す

    実際にPRへコメントを投稿する前に、生成されるコメント内容をログで確認できます。

    bash 
    java -jar target/gitbucket-llm-reviewer.jar --config config.yml --once --dry-run

  5. 常駐モードで起動する

    問題なければ --once --dry-run を外して起動します。polling.intervalSeconds 毎にポーリングを続け、 SIGTERMで安全に停止します。

    bash 
    java -jar target/gitbucket-llm-reviewer.jar --config config.yml

05.review.yml リファレンス

レビュー対象リポジトリ側のルートに置く設定です。存在しない、または解析に失敗した場合は観点が0件となり、 そのリポジトリのレビュー自体をスキップします(デフォルト観点にフォールバックすることはありません)。

キー型デフォルト説明
languagestringjaサマリ・指摘のレビュー言語
perspectives(string | object)[][](=レビュー自体をスキップ)リポジトリ全体に適用する共通観点。各要素はスカラー文字列、または perspective/context を持つオブジェクトのどちらでもよい
perspectives[].perspectivestring—オブジェクト形式で書く場合の観点テキスト(スカラー文字列形式の値に相当)
perspectives[].contextstring[][].review/ からの相対パス。この観点が適用されるレビュー時、RAG検索を介さず常にそのままLLMへ渡す追加コンテキスト(任意)
paths.<glob>.perspectives(string | object)[][]指定globにマッチする変更ファイルにのみ追加される観点(モノレポ対応)。要素の形式は共通の perspectives と同じで、context も同様に使える
paths.<glob>.inheritbooleantruefalse にすると、このglobにマッチしたファイルには共通観点・共通knowledgeBaseを適用しない
paths.<glob>.knowledgeBasestring[][]このglobにマッチする変更ファイルにのみ追加されるコーディング規約文書パス(モノレポ対応。rag.enabled=true時のみ使用)
excludestring[][]diffから除外するglob(生成物・minifyファイル等)
contextFilesstring[][]Nパスを待たず常にLLMへ渡すファイル(README等)
knowledgeBasestring[][]RAG検索対象のコーディング規約文書パス(リポジトリ共通分。rag.enabled=true時のみ使用)
maxCommentsint10PRコメントに表示する指摘事項の最大件数。超過分は件数のみ注記

観点別の追加コンテキスト(.review/ フォルダ)

.review.yml と同階層に .review/ フォルダを置き、perspectives (または paths.<glob>.perspectives)の各要素を perspective/context を持つオブジェクト形式で書くと、その観点専用のMarkdownファイルを紐づけられます。 ドメイン知識・アーキテクチャ・独自DSL知識・独自コーディングルール・厳守事項などを、カテゴリごとに .review/ 配下のサブフォルダへ分類して管理できます。

.review.yml(抜粋) 
perspectives:
  - セキュリティ(インジェクション、認可漏れ)   # 従来通りのスカラー文字列も引き続き使える
  - perspective: 独自DSLのバリデーションルール整合性
    context:
      - dsl/spec.md                     # .review/dsl/spec.md を読み込む
      - must-follow/security-checklist.md
ディレクトリ構成の例 
.review.yml
.review/
├── domain-knowledge/
│   └── payment-flow.md
├── architecture/
│   └── overview.md
├── dsl/
│   └── spec.md
├── coding-rules/
│   └── naming.md
└── must-follow/
    └── security-checklist.md
knowledgeBase との違い

knowledgeBase(RAG)はベクトル類似検索で「関連しそうなチャンク」を拾う仕組みですが、 perspectives[].context で指定したファイルは検索を介さず、その観点が適用されるレビューでは 常に全文がそのままLLMへ渡されます。「この観点をチェックする際は必ずこの内容を踏まえてほしい」 という用途に向きます。

モノレポでの観点解決の例

下記の .review.yml の場合、変更ファイルごとに適用される観点は図2のように解決されます。 backend/** は inherit: false のため、共通観点は適用されません。

.review.yml(抜粋) 
perspectives:
  - セキュリティ上の懸念(インジェクション、認可漏れ)
  - 既存コードとの命名・設計の一貫性
paths:
  "frontend/**":
    perspectives:
      - React hooksの依存配列漏れ
    inherit: true   # 共通観点も適用される
  "backend/**":
    perspectives:
      - トランザクション境界の妥当性
    inherit: false  # 共通観点・共通knowledgeBaseは適用されない
    knowledgeBase:
      - backend/docs/coding-standards.md  # rag.enabled=true時のみ使用

図2: README.md は共通観点のみ、Button.tsx は共通観点と frontend/** 固有観点の両方、 UserService.java は inherit: false のため backend/** 固有観点のみが適用されます。

07レビューの流れ(バッチ分割・Nパス)

PR全体のdiffが review.maxDiffChars を超える場合、まず DiffBatcher が ファイル境界(diff --git a/... b/... 行)を尊重して複数バッチに分割します(切り捨てではなく、 各ファイルをレビュー対象に残す設計です)。以降の観点解決・RAG検索・Nパスはバッチ毎に独立して実行され、 全バッチのfindingsとsummaryを結合してからPRコメントを投稿します。 diffだけでは判断がつかない変更に対しては、各バッチ内でLLMが追加ファイルを要求でき、ツールはそれを取得して 再度同じスキーマで問い合わせます。この往復を review.maxPasses 回まで繰り返します。 rag.enabled: true の場合、各バッチのdiffをクエリとしてベクトル検索による参考情報を事前提示します(詳細は「09 RAGによるコンテキスト拡張」)。

大量修正PRのバッチ分割

状況挙動
PR全体のdiffが maxDiffChars 以下1バッチとして通常どおりレビュー
超過するが maxDiffBatches 以内に収まるファイル境界で複数バッチに分割し、バッチ毎にLLMへ送信。findings/summaryをマージして1組のPRコメントとして投稿
分割後のバッチ数が maxDiffBatches を超える先頭から上限数のバッチのみレビュー。超過分のファイルはサマリコメントの「サイズ上限のため今回のレビュー対象外となったファイル」セクションに明記
1ファイル単体が maxDiffChars を超えるそのファイルだけ先頭カットの単独バッチ(truncated=true)として処理

疑似インラインコメントのスニペット引用・増分レビューの対象範囲表示は、バッチ分割前のPR全体diffに基づきます。 観点解決・RAG検索・fullFileContextEnabled による全文コンテキスト収集は、各バッチに含まれる変更ファイルに絞って行われます。

図3: need_more_context でも残りパス数がある限りは再送信を繰り返し、上限に達すると強制的に complete としての出力を指示してから投稿処理に進みます。JSONとしてパースできない応答は1回だけ矯正リトライします。

構造化出力スキーマ

LLMには次のJSONスキーマ1つのみを出力するよう指示しています。

json 
{
  "status": "complete" | "need_more_context",
  "requestedFiles": [ { "path": "...", "reason": "..." } ],
  "summary": "変更内容の要約(status=completeの場合は必須)",
  "findings": [
    { "file": "...", "line": 123,
      "severity": "error"|"warning"|"info",
      "perspective": "...", "comment": "..." }
  ]
}

complete レビュー完了、コメントを投稿します。 need_more_context 追加ファイルが必要。 パース失敗 矯正リトライしても解析できない場合はそのPRのレビューを失敗として記録します。

08メンションでの追質問/追レビュー

PRコメントでBot自身のGitBucketアカウントにメンションすると、07のポーリングによる自動レビューとは独立した経路で、 追質問や追加レビュー依頼にLLMが応答します。.review.yml の有無に関わらず常時動作するため、 観点が0件で自動レビュー自体はスキップされているリポジトリでも、この経路だけは機能します。

PRコメントの例 
@review-bot このnullチェックはなぜ必要ですか?エラーハンドリングもあわせて確認してください。

Botユーザー名の解決

メンション対象として認識する自分自身のユーザー名は、起動時に一度だけ次の優先順位で解決されます。 どちらの場合も起動ログの メンション応答機能を有効化します(botUsername=...) でどの名前を監視しているか確認できます。解決に失敗した場合はメンション応答機能のみが無効化され、 通常のポーリングレビューは継続して動作します(起動自体は失敗しません)。

優先度条件採用される値
1gitbucket.botUsername が設定されているその値をそのまま使用(APIは呼ばない)
2未設定(空文字)GET /api/v3/user の応答(gitbucket.token の持ち主)から自動解決
実運用でのアカウント分離

自動解決を使う場合、Bot用に専用のGitBucketアカウントを作成しそのアカウントのトークンを gitbucket.token に設定することを推奨します。人間の投稿者と同じアカウントのトークンを使うと、 そのアカウント自身が投稿したコメントは常に「Bot自身の発言」として除外されるため、そのアカウントからの メンションには反応できません。

動作の詳細

項目挙動
呼び出せる人PRにコメントできる人なら誰でも(許可リストによる制限はない)
検知タイミング次回のポーリング(polling.intervalSeconds)でPRのコメント一覧を確認した時
二重応答防止PR毎の処理済み最終コメントIDを state.mentionStateFilePath に永続化。同じコメントに二度応答しない
初めて観測したPR既存のメンションには応答せず、その時点の最新コメントIDを基準点として記録するのみ(デプロイ直後の一括応答を防止)
コメント編集での追加検知されない(コメントIDが変わらないため)。新規コメントとして投稿する必要がある
応答失敗時そのコメント以降の処理を打ち切り、次回のポーリングで再試行する(質問をサイレントに握りつぶさない)

.review.yml の有無による観点の扱い

LLMへのプロンプトには常に「メンションコメント本文」がそのまま渡されますが、.review.yml から観点が解決できた場合はそれも併せて渡されます。観点が無い場合はメンション文面そのものが観点になり、 観点がある場合はそれを踏まえつつメンションの質問に答えます(観点が上書き・無視されることはありません)。

状態プロンプトに含まれる内容
.review.yml あり(観点を解決できた)「## レビュー観点」セクション(このリポジトリの観点一覧)+「## ユーザーからの質問/追加レビュー依頼」セクション(メンション本文)の両方
.review.yml なし/観点0件「## ユーザーからの質問/追加レビュー依頼」セクション(メンション本文)のみ。この文面が実質的な観点として扱われる

diff取得・追加コンテキストファイルの収集・RAGによる参考情報の付与・need_more_context による追加ファイル要求(「07 レビューの流れ」と同じ往復ループ)は、通常のレビューと同様にこの経路でも行われます。 メンション応答ではバッチ分割は行わず、review.maxDiffChars を超えるdiffは従来どおり先頭カットで1回のLLM呼び出しに収めます。 応答は新規のPRコメントとして投稿されます。

09RAGによるコンテキスト拡張

rag.enabled: true にすると、langchain4j経由でリポジトリコード全体と.review.ymlの knowledgeBaseに指定したコーディング規約文書をベクトル検索し、各バッチのdiffに関連しそうなチャンクを 「参考情報」としてプロンプトへ事前提示します。07のNパス(need_more_context)を置き換えるものではなく補完するもので、 RAGが拾えなかった/精度が不安な情報は従来どおりLLMがNパスで明示要求できます。

2種類のインデックス

対象更新タイミング変更検知
リポジトリコード全体初回は全量インデックス、以降はPRのheadSha更新に合わせて変更ファイルのみ増分インデックス前回インデックス済みheadShaとの比較(RagIndexStateStore)
コーディング規約文書(knowledgeBase)参照される都度、内容の変更有無を確認ファイル内容のSHA-256ハッシュ比較

いずれもlangchain4jのInMemoryEmbeddingStoreを用い、rag.indexDir配下にJSONとして永続化されるため、 プロセスを再起動してもインデックスの再構築コストは発生しません(内容に変化がない限り)。

プロンプトへの反映

検索結果は「関連コード候補」「関連コーディング規約抜粋」という見出しで、通常のdiff・観点セクションより前に挿入されます。 いずれも「自動検索による参考情報であり正確性は保証されない」旨を明記した上でLLMに渡されます。 embeddingサーバーへの接続に失敗した場合は空の結果として扱われ、RAGなしの従来どおりのレビューフローにフォールバックします (レビュー自体が失敗することはありません)。

精度に関する注意

ベクトル類似検索は「意味的に近い」チャンクを返すものであり、呼び出し関係のような構造的な依存関係を正確に特定できるとは限りません。 コーディングレビューの正確性が特に重要な確認(呼び出し先の実装確認等)は、RAGの結果を鵜呑みにせず、 引き続きNパスによるファイル全文取得に委ねる設計になっています。ローカルの小型embeddingモデルほどこの傾向は強くなるため、 rag.minScoreを低くしすぎないことを推奨します。

設定例(.review.yml)

.review.yml(抜粋) 
knowledgeBase:                # リポジトリ共通のコーディング規約文書
  - docs/coding-standards.md
  - docs/adr/*.md

設定項目の一覧は「04 config.yml リファレンス」の rag の節を参照してください。

10状態管理と冪等性

state.filePath(デフォルト ./data/review-state.json)にPR毎のレビュー済み状態を永続化し、 同じコミットへの二重レビューを防ぎます。

review-state.json 
{
  "root/sample-repo#3": {
    "reviewedHeadSha": "a1b2c3d...",
    "reviewedAt": "2026-07-24T20:45:21Z",
    "status": "reviewed",
    "failureCount": 0
  }
}
判定ロジック(needsReview)
状況結果
該当PRの記録が存在しない(新規PR)レビューする
記録はあるが head.sha が変わった(push更新)レビューする
同じ head.sha で status: "failed"再試行する
同じ head.sha で status: "reviewed" または "skipped"スキップ

レビュー処理が例外で失敗すると failureCount が加算され、3回連続で失敗すると status: "skipped" となり、それ以降は同一コミットへの無限リトライを行いません。push更新があれば failureCount はリセットされ、再度レビュー対象になります。

メンション応答の状態(mention-state.json)

「08 メンションでの追質問/追レビュー」用に、state.mentionStateFilePath (デフォルト ./data/mention-state.json)へPR毎の「処理済み最終コメントID」を永続化します。 review-state.json とは別ファイル・別の判定ロジックで、headShaではなくコメントID(単調増加)のみを追跡します。

mention-state.json 
{
  "root/sample-repo#3": 21
}

値は「このPRでID 21までのコメントは処理済み」を意味し、次回ポーリングでは id > 21 のコメントのみをメンション検知の対象にします。--dry-run 時は review-state.json と同様にこのファイルへの書き込みも行われません。

11文字コードの扱い

重要

レビュー対象のソースコードは必ずしもUTF-8とは限りません(Shift_JIS・EUC-JP等の日本語コードベースも実運用では多く存在します)。

本ツールは juniversalchardet によるバイト列からの文字コード自動判定を、 JGitでのファイル読み込み・diff生成・GitBucket contents APIによる生コンテンツ取得のすべてで行います。 判定できない場合はUTF-8にフォールバックします。これにより、Shift_JIS等でコミットされたソースファイルであっても、 文字化けした内容がLLMに渡ることを防ぎます。

ただし、コミット単位パッチ連結によるAPIフォールバック経路(JGitのfetchに失敗した場合のみ使用)は、 GitBucketサーバー側が生成したJSON応答の文字列をそのまま利用するため、サーバー側のエンコーディング処理に依存します。

12トラブルシューティング

JGitのfetchが認証エラーになる

未設定時はAPIトークンをユーザー名・パスワード両方としてBasic認証を試みますが、 GitBucketの構成によっては通らないことがあります。config.yml の gitbucket.gitUsername / gitbucket.gitPassword に実際のGitBucketアカウントの 認証情報を明示的に設定してください。

PRを検出しているのにレビューされずスキップされる

ログに「適用可能な観点が0件のためレビューをスキップします」と出ていないか確認してください。 対象リポジトリのベースブランチ(PRのマージ先)ルートに .review.yml が 無い、解析に失敗している、または perspectives が空(モノレポの場合は該当globにもマッチしない) と、このメッセージとともにレビュー自体がスキップされます。.review.yml は サブフォルダに置いても読み込まれません。必ずリポジトリルートに配置してください。

PRにコメントが投稿されない

--dry-run を付けたまま起動していないか確認してください。--dry-run 時はログに出力するのみで、 実際の投稿は行いません。また、ログに GitBucketApiException が出ていないか確認してください (PR単位・リポジトリ単位で例外は隔離され、他のPR/リポジトリの処理は継続します)。

同じPRが何度もレビューされる / 逆に更新してもレビューされない

state.filePath のファイルが書き込み可能な場所を指しているか確認してください。 書き込みに失敗すると次回起動時に状態が失われ、再レビューが発生します。 逆にレビューされない場合は、該当キー(owner/repo#番号)の status が "skipped"(3回失敗済み)になっていないか確認してください。

diffが不完全、またはmerge-base差分と違う内容になる

ログに「JGitによるdiff取得に失敗したためAPIフォールバックを使用します」と出ていないか確認してください。 フォールバック経路はコミット単位パッチの連結による近似であり、厳密なmerge-base差分ではありません。 JGitのfetchが安定して成功するよう、まずは認証設定を見直してください。

LLMの応答がJSONとして解析できずレビューが失敗する

1回だけ矯正リトライ(「スキーマ通りのJSONのみを出力してください」という指示を追加送信)を行いますが、 それでも解析できない場合はレビュー失敗として記録されます。llm.temperature を下げる、 使用モデルがJSONモード(response_format)に対応しているか確認する、といった対処が有効です。

大量修正PRで一部のファイルがレビューされていない

サマリコメントに「サイズ上限のため今回のレビュー対象外となったファイル」セクションが付いていないか確認してください。 付いている場合、review.maxDiffBatches の上限により今回のレビューから除外されたファイルです。 maxDiffChars を上げて1バッチあたりの容量を増やす、または maxDiffBatches を上げて 許容バッチ数を増やすことで対応できます(いずれもLLM呼び出し回数・プロンプトサイズ・所要時間が増えます)。

指摘件数が想定より少ない

.review.yml の maxComments はPRコメントに表示する件数の上限です。 超過分は「他N件の指摘は表示上限のため省略されました」という注記になります(LLM自体はより多く検出している場合があります)。

RAG(rag.enabled: true)を有効にしてもレビュー内容が変わらない

embeddingサーバー(rag.embeddingBaseUrl)への接続に失敗した場合、RAG検索は空の結果として扱われ、 ログに警告を出したうえで通常どおりレビューが継続されます(レビュー自体は失敗しません)。ログに 「RAG検索に失敗したため、参考情報なしで継続します」が出ていないか確認してください。また、初回のリポジトリ全量インデックス構築には 時間がかかるため、大きめのリポジトリでは1回目のレビューでは十分な検索結果が得られないことがあります。

PRコメントで @botname にメンションしても応答されない

まず起動ログの メンション応答機能を有効化します(botUsername=...) を確認し、 意図した名前が表示されているか確認してください。表示されず「Botユーザー名を解決できなかったため、 メンション応答機能を無効化します」と出ている場合は、gitbucket.token の持ち主のユーザー名取得 (GET /api/v3/user)に失敗しています。gitbucket.botUsername を明示的に設定してください。 また、メンションした投稿者がBot自身と同じアカウントだと自己投稿として除外され反応しません (「08」の「実運用でのアカウント分離」を参照)。デプロイ直後・そのPRを初めて観測した回はまだ存在するメンションに 応答しない仕様のため、応答させたい場合は基準点記録後にあらためてメンションを投稿してください。

同じメンションに何度も応答される / 逆に一度も応答されない

state.mentionStateFilePath のファイルが書き込み可能な場所を指しているか確認してください。 review-state.json と同様、書き込みに失敗すると次回起動時に基準点が失われ、 過去のメンションへ再度応答してしまうことがあります。一度も応答されない場合は、直前の応答処理が例外で 失敗し、そのコメント以降の処理が打ち切られたまま次回ポーリングで再試行され続けている可能性があるため、 MentionReplyOrchestrator 関連のWARNINGログを確認してください。
