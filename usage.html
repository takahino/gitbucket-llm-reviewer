gitbucket-llm-reviewer 詳細ガイド

GitBucket のプルリクエストをポーリングで監視し、OpenAI互換API経由のローカルLLMで 自動コードレビューを行うJava 21製アプリケーションの運用マニュアルです。 セットアップから設定ファイルの全項目、Nパスによる全体整合チェックの内部動作まで、 実際に運用する上で必要な情報をまとめています。

→ すぐに動かす config.yml 全項目 .review.yml 全項目 Nパスの仕組み うまく動かない時

01全体像

1プロセスの常駐アプリケーションが、監視対象リポジトリを定期的に走査します。 diffの取得はGitBucketのgit smart HTTPに対するJGitフェッチを主経路とし、 失敗した場合のみREST APIのコミット単位パッチ連結にフォールバックします。

図1: 実線の矢印がJGit経由の主経路、破線がAPIフォールバック経路。LLMとReviewOrchestratorの間の点線ループは need_more_context による追加ファイル要求の往復を表す(詳細は「07 レビューの流れ」を参照)。

項目要件
Java21 以上
Maven3.9 以上
GitBucket稼働中のインスタンス(4.46.1で動作確認済み)とAPIトークン

03セットアップ

初回起動までの実際の手順です。上から順に実行してください。

  1. ビルドする

    プロジェクトルートで実行可能なfat-jarを生成します。

    bash 
    # target/gitbucket-llm-reviewer.jar が生成される
mvn package

  2. ツール側設定ファイルを作成する

    config.example.yml を config.yml としてコピーし、実際の値を設定します。 config.yml は .gitignore 済みなので、実トークンをコミットしてしまう心配はありません。

    bash 
    cp config.example.yml config.yml

    最低限、以下の3項目は必ず自分の環境の値に書き換えてください(各項目の意味は「04 config.yml リファレンス」で解説)。

    config.yml(抜粋) 
    gitbucket:
  baseUrl: http://localhost:8080   # 自分のGitBucketのURL
  token: "xxxxxxxx"            # GitBucketで発行したAPIトークン
repositories:
  - owner: root               # 監視したいリポジトリのowner
    name: sample-repo         # 監視したいリポジトリ名

  3. リポジトリ側にレビュー観点を配置する(任意)

    review.example.yml を参考に、レビュー対象リポジトリのルートに .review.yml として配置します。配置しない場合はデフォルトの観点(セキュリティ・命名一貫性・エッジケース)で継続されます。

    bash 
    # レビュー対象リポジトリ側での作業
cp review.example.yml .review.yml
git add .review.yml && git commit -m "add review perspectives"

  4. まずは --once --dry-run で試す

    実際にPRへコメントを投稿する前に、生成されるコメント内容をログで確認できます。

    bash 
    java -jar target/gitbucket-llm-reviewer.jar --config config.yml --once --dry-run

  5. 常駐モードで起動する

    問題なければ --once --dry-run を外して起動します。polling.intervalSeconds 毎にポーリングを続け、 SIGTERMで安全に停止します。

    bash 
    java -jar target/gitbucket-llm-reviewer.jar --config config.yml

05.review.yml リファレンス

レビュー対象リポジトリ側のルートに置く設定です。存在しない、または解析に失敗した場合はデフォルト観点で継続します。

キー型デフォルト説明
languagestringjaサマリ・指摘のレビュー言語
perspectivesstring[]デフォルト観点3件リポジトリ全体に適用する共通観点
paths.<glob>.perspectivesstring[][]指定globにマッチする変更ファイルにのみ追加される観点(モノレポ対応)
paths.<glob>.inheritbooleantruefalse にすると、このglobにマッチしたファイルには共通観点を適用しない
excludestring[][]diffから除外するglob(生成物・minifyファイル等)
contextFilesstring[][]Nパスを待たず常にLLMへ渡すファイル(README等)
maxCommentsint10PRコメントに表示する指摘事項の最大件数。超過分は件数のみ注記

モノレポでの観点解決の例

下記の .review.yml の場合、変更ファイルごとに適用される観点は図2のように解決されます。 backend/** は inherit: false のため、共通観点は適用されません。

.review.yml(抜粋) 
perspectives:
  - セキュリティ上の懸念(インジェクション、認可漏れ)
  - 既存コードとの命名・設計の一貫性
paths:
  "frontend/**":
    perspectives:
      - React hooksの依存配列漏れ
    inherit: true   # 共通観点も適用される
  "backend/**":
    perspectives:
      - トランザクション境界の妥当性
    inherit: false  # 共通観点は適用されない

図2: README.md は共通観点のみ、Button.tsx は共通観点と frontend/** 固有観点の両方、 UserService.java は inherit: false のため backend/** 固有観点のみが適用されます。

07レビューの流れ(Nパス)

diffだけでは判断がつかない変更(呼び出し元だけが変わり、呼び出し先の実装が見えていない等)に対応するため、 LLMは追加ファイルを要求できます。ツールはそれを取得して再度同じスキーマで問い合わせます。この往復を review.maxPasses 回まで繰り返します。

図3: need_more_context でも残りパス数がある限りは再送信を繰り返し、上限に達すると強制的に complete としての出力を指示してから投稿処理に進みます。JSONとしてパースできない応答は1回だけ矯正リトライします。

構造化出力スキーマ

LLMには次のJSONスキーマ1つのみを出力するよう指示しています。

json 
{
  "status": "complete" | "need_more_context",
  "requestedFiles": [ { "path": "...", "reason": "..." } ],
  "summary": "変更内容の要約(status=completeの場合は必須)",
  "findings": [
    { "file": "...", "line": 123,
      "severity": "error"|"warning"|"info",
      "perspective": "...", "comment": "..." }
  ]
}

complete レビュー完了、コメントを投稿します。 need_more_context 追加ファイルが必要。 パース失敗 矯正リトライしても解析できない場合はそのPRのレビューを失敗として記録します。

08状態管理と冪等性

state.filePath(デフォルト ./data/review-state.json)にPR毎のレビュー済み状態を永続化し、 同じコミットへの二重レビューを防ぎます。

review-state.json 
{
  "root/sample-repo#3": {
    "reviewedHeadSha": "a1b2c3d...",
    "reviewedAt": "2026-07-24T20:45:21Z",
    "status": "reviewed",
    "failureCount": 0
  }
}
判定ロジック(needsReview)
状況結果
該当PRの記録が存在しない(新規PR)レビューする
記録はあるが head.sha が変わった(push更新)レビューする
同じ head.sha で status: "failed"再試行する
同じ head.sha で status: "reviewed" または "skipped"スキップ

レビュー処理が例外で失敗すると failureCount が加算され、3回連続で失敗すると status: "skipped" となり、それ以降は同一コミットへの無限リトライを行いません。push更新があれば failureCount はリセットされ、再度レビュー対象になります。

09文字コードの扱い

重要

レビュー対象のソースコードは必ずしもUTF-8とは限りません(Shift_JIS・EUC-JP等の日本語コードベースも実運用では多く存在します)。

本ツールは juniversalchardet によるバイト列からの文字コード自動判定を、 JGitでのファイル読み込み・diff生成・GitBucket contents APIによる生コンテンツ取得のすべてで行います。 判定できない場合はUTF-8にフォールバックします。これにより、Shift_JIS等でコミットされたソースファイルであっても、 文字化けした内容がLLMに渡ることを防ぎます。

ただし、コミット単位パッチ連結によるAPIフォールバック経路(JGitのfetchに失敗した場合のみ使用)は、 GitBucketサーバー側が生成したJSON応答の文字列をそのまま利用するため、サーバー側のエンコーディング処理に依存します。

10トラブルシューティング

JGitのfetchが認証エラーになる

未設定時はAPIトークンをユーザー名・パスワード両方としてBasic認証を試みますが、 GitBucketの構成によっては通らないことがあります。config.yml の gitbucket.gitUsername / gitbucket.gitPassword に実際のGitBucketアカウントの 認証情報を明示的に設定してください。

PRにコメントが投稿されない

--dry-run を付けたまま起動していないか確認してください。--dry-run 時はログに出力するのみで、 実際の投稿は行いません。また、ログに GitBucketApiException が出ていないか確認してください (PR単位・リポジトリ単位で例外は隔離され、他のPR/リポジトリの処理は継続します)。

同じPRが何度もレビューされる / 逆に更新してもレビューされない

state.filePath のファイルが書き込み可能な場所を指しているか確認してください。 書き込みに失敗すると次回起動時に状態が失われ、再レビューが発生します。 逆にレビューされない場合は、該当キー(owner/repo#番号)の status が "skipped"(3回失敗済み)になっていないか確認してください。

diffが不完全、またはmerge-base差分と違う内容になる

ログに「JGitによるdiff取得に失敗したためAPIフォールバックを使用します」と出ていないか確認してください。 フォールバック経路はコミット単位パッチの連結による近似であり、厳密なmerge-base差分ではありません。 JGitのfetchが安定して成功するよう、まずは認証設定を見直してください。

LLMの応答がJSONとして解析できずレビューが失敗する

1回だけ矯正リトライ(「スキーマ通りのJSONのみを出力してください」という指示を追加送信)を行いますが、 それでも解析できない場合はレビュー失敗として記録されます。llm.temperature を下げる、 使用モデルがJSONモード(response_format)に対応しているか確認する、といった対処が有効です。

指摘件数が想定より少ない

.review.yml の maxComments はPRコメントに表示する件数の上限です。 超過分は「他N件の指摘は表示上限のため省略されました」という注記になります(LLM自体はより多く検出している場合があります)。
